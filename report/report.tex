        \subsection{Subpackages}
            We created a subpackage named \mintinline{text}{cs} located at \mintinline{text}{it.unitn.ds.cs}.
            The code related to our abstractions is located under the \mintinline{text}{cs} package.
            Instead of placing message classes inside the class of the receiver (as suggested in the labs), we put all message classes in a subpackage \mintinline{text}{it.unitn.ds.cs.messages}.
            Inside this package, messages are divided based on who is the sender.
        \subsection{Naming Convention}
            To easily identify our classes all class names have the prefix \mintinline{text}{CS}.
    \section{Design}
        To keep the explanation concise, we focus solely on the aspects that complement the project instructions:\\
        our assumptions, additional features, and custom solutions.
        \subsection{Assumptions}
            \subsubsection{Project Instructions}
                \begin{itemize}
                    \item Communication channels are assumed to be reliable and FIFO
                    \item A strict majority of replicas never crashes.
                    \item Replicas fail by crashing and do not recover.
                    \item Static system membership: no new replicas may join after initialization.
                \end{itemize}
            \subsubsection{UUID uniqueness}
                We assume that the generated UUIDs are unique. Replicas independently generate UUIDs and so technically it can happen that two independent UUIDs match, making them not unique.\\
                It has to be noted that we rely on the UUID class included in the Java SDK which offers some guarantees.\\
                The documentation for the method \mintinline{java}{public static UUID randomUUID()} states: "The UUID is generated using a cryptographically strong pseudo random number generator."\\
                We can also look at the problem from a statistical point of view. A UUID represents a 128bit value, the chance of two random UUID being identical is \( \frac{1}{2^{128}} = ~\sim3 \times 10^{-39} \), which is negligible.
            \subsubsection{Replica Crash Detection}
                Since channels are reliable, if a replica does not Ack messages for which an Ack is expected (such as Update or Election messages), that replica can be considered crashed.
            \subsubsection{Timeout values}
                The timeouts values are all based on \mintinline{java}{AbstractReplica.getMaxLatencyPlusTolerance()} which internally takes into account the network latency and the number of active replicas.
                Through trial and error we found values that made the system responsive and avoided false positives.
                Additionally, by calculating timeouts based on such parameters rather than relying on constant values, the system should be able to adapt to larger groups of replicas.
        \subsection{AskSystem}
            We initially attempted to follow Akka Ask pattern using the provided \mintinline{java}{ask()} method, which returns a\\
            \mintinline{java}{CompletionStage} (future) that completes when a response is received. However, the future is completed on whatever thread delivers the response which is not guaranteed to be the requesting sending actor thread.
            Mutating actor state inside the callback introduce race conditions. \href{https://doc.akka.io/japi/akka-core/2.10/akka/pattern/Patterns.html#ask(akka.actor.ActorRef,java.lang.Object,akka.util.Timeout)}{Akka ask documentation}:
            \textit{"do not call methods or access mutable state [...] from within the callback. This [...] may introduce synchronization bugs and race conditions. [...] there is not yet a way to detect these illegal accesses at compile time."}

            The standard solution is to use \mintinline{java}{pipeToSelf()}, which delivers the result as a message to the actor mailbox, where it is processed like any other message. 
            But the project requires to use the \mintinline{java}{tell()} method of the codebase that emulates network latency. And this cannot be done using Akka own methods.
            
            Therefore we designed our own wrapper called askSystem built on top of the custom \mintinline{java}{tell()} to emulate the ask pattern which makes very easy handling timeouts. AskSystem enables an actor to send messages and register a callback to be executed when a response is received and/or when the specified timeout expires. All messages sent through AskSystem must extend \mintinline{java}{CSAskMessage} which has an UUID as an attribute used to correlate a request with a response and trigger the correct callback.

            When a message is sent a \mintinline{java}{CSAskTimeout} to self is scheduled through a timer. If the response is received in time the timer is canceled and the callback fired, otherwise if the \mintinline{java}{CSAskTimeout} message is received the callback is still fired but with the information that the timer expired.

            Example: in Figure \ref{fig:protocol_diagram}, the UUIDs used by the AskSystem are shown as superscript and color coded for each message.

        \subsection{Update Protocol} \label{subsec:update_protocol}
            For write requests, we designed replicas so that they immediately keep track of the request in their history instead of logging it only when the Update message is received.
            This way, if the coordinator crashes before processing the request, the replica which forwarded it still has track of it and can try again after the election.
            This choice introduces a problem: replicas need to be able to correlate the request forwarded to the coordinator with the Update message they will receive later.

            Example:
            \begin{itemize}
                \item ReplicaA and replicaB send WriteRequest \mintinline{text}{(index=2, value=7)}
                \item Coordinator sends Update \mintinline{text}{(<0, 1>, index=2, value=7)}
                \item Coordinator sends Update \mintinline{text}{(<0, 2>, index=2, value=7)}
            \end{itemize}
            Problem: there is now way of matching an update to the correct request

            Solution:
            each replica appends to the Request message a privately generated UUID. The coordinator appends to the Update message the UUID contained in the request. When an Update message is received each replica checks for a matching UUID which binds the Update to its Request.
            \subsubsection{Crash Detection}
                During the update protocol the coordinator can detect crashed replicas that do not answer with an Ack.
                
                The coordinator after detecting a crash removes the replica from its list of active replicas and sends a \mintinline{java}{CSCrashNotice} message to the previous replica so that it can update its own list of active replicas and the pointer to the next replica.

                Originally crashed replicas are discovered only during the Election process when passing the message through the ring.
                This extra measure speeds up the Election process avoiding some unnecessary timeouts as crashed replicas can be discovered before the Election.
            \subsection{Updates Logging}
                Update logging is taken care by the class \mintinline{java}{CSUpdateLogger}. Every replica has an attribute \mintinline{java}{updateLogger} which is used to:
                \begin{itemize}
                    \item Log write requests coming from clients
                    \item Log updates coming from the coordinator
                \end{itemize}

                As discussed in section \ref{subsec:update_protocol}, it is important to log requests from the moment they are received from the client, as during the coordinator recovery (subsection \ref{subsec:recovery}) we process not only the updates that did not complete, but also the requests that have not yet been fulfilled.

                As will be discussed further in section \ref{subsec:update_logging}, the class enables updates to be identified in two ways:
                \begin{itemize}
                    \item The UUID generated by the replica when the request of the client is received.
                    \item The update key \mintinline{text}{<e,i>} that the coordinator uses in the update protocol.
                \end{itemize}
        \subsection{Coordinator}
            The coordinator acts differently from replicas in almost every operation. We decided to introduce custom behavior rather than making it behave similarly to replicas, as this would have required sending messages to itself.

            As a result all local operations are performed immediately, skipping the sending of any message to itself.
            \subsubsection{Heartbeat}
                The heartbeat detection is not done through the AskSystem which works only during update processing. We instead opted for a timer based system that in contrast works also during idle periods.

                When a replica becomes a coordinator a recurring message to self is scheduled, which upon arriving triggers the broadcast of the heartbeat message to all replicas. Each replica schedules a recurring message to self too, which triggers a check that the heartbeat has been received during the interval.
                
                A flag is raised when a heartbeat is received and lowered after every check. If the flag is not found raised during a check, an election is initiated.

                The replicas start checking for a heartbeat with some delay to allow the coordinator to spin up. In addition the checking interval is a little longer than the beat interval to allow for slowdowns in the communication and processing. Everything combined absorbs propagation delay and avoids false positives.
        \subsection{Election}
            The ring structure needed during the election is maintained through a series of pointers. Each replica has an attribute \mintinline{java}{next} which stores the ID of the following replica in the ring.
            \subsubsection{Crash detection}
                When forwarding the election message through the ring if the timeout for an Ack expires the replica knows that its \mintinline{java}{next} has crashed so it can remove it from its list of active replicas and update its next
            \subsubsection{Non Blocking}
                To make sure that the election process terminates we do four things:
                \begin{enumerate}
                    \item To avoid the circulation of duplicated Election messages replicas consider only the message sent by the replica with the highest ID. Election messages carry a value called \mintinline{java}{initiatorId}, and replicas keep track of the \mintinline{java}{initiatorId} of the message they are currently considering. When any election message is received, a replica drops it if the \mintinline{java}{initiatorId} is lower that the tracked one (Figure \ref{code:electioncondition}).
                    \item If a crash is detected the replica tries to contact the following active replica. The attempts continue indefinitely until a replica correctly sends back an Ack.
                    \item When passing the election message with the chosen coordinator, if the previous replica in the ring detects the crash of the winner it removes it from the election message, computes the new winner and continues to circulate the message.
                    \item As a catch-all solution for any other case every replica start a timer at the start of every election. If the timer expires the replica starts a new election attempt. In a similar fashion to point 1. only the most recent attempt is considered (Figure \ref{code:electioncondition}).
                \end{enumerate}

} else {

        \subsubsection{WriteOk Timeout}
            When a replica sends (through \mintinline{text}{ask()}) its Ack for an update, a timer starts. To avoid the timer from expiring we need to send a WriteOk containing the correct askUUID to the replica.
            The problem is that the coordinator must broadcast the WriteOk message when the quorum is reached.

            Our solution instead is for each replica to keep a map of the update key and the askUUID used to send the Ack.
            In \mintinline{java}{HandleUpdate()} the mapping is recorded in \mintinline{java}{Map<CSUpdateKey, UUID> updatesAskUUIDs}.

public final void handleWriteOk(CSWriteOk msg) {
    UUID askUUID = this.updatesAskUUIDs.get(msg.getKey());
    this.askSystem.handleResponse(new CSWriteOk(msg.getKey(), askUUID));
}
            \end{minted}

        \subsection{Update Logging} \label{subsec:update_logging}
            We leverage two different HashMaps:
            \begin{itemize}
                \item \mintinline{java}{Map<UUID, CSUpdateData> updates}
                \item \mintinline{java}{Map<CSUpdateKey, UUID> keyToUUIDBindings}
            \end{itemize}

            When a replica receives a WriteRequest from the client the coordinator has not assigned a key yet. The only identifying information is the generated UUID, so the update is first inserted into \mintinline{java}{updates}.

            When replica receives an Update message it binds the key to the UUID through \mintinline{java}{keyToUUIDBindings}.

            Upon receiving the WriteOk, which identifies the update only by its CSUpdateKey, we need to gather the update data chaining the two HashMaps: \mintinline{java}{updates.get(keyToUUIDBindings.get(key))}. The data contains information on the write to apply (index and value) and the reference to the client that is waiting for the WriteResult.
